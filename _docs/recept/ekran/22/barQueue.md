# `barQueue` · очередь заказов у работника бизнеса

**Зритель:** работник бизнеса (роль `worker` из шага 14) — очередь ТОЛЬКО своего
направления. Бар и куратор видят её, как видели. Экран не новый: шаг 22 его
РАЗМОРАЖИВАЕТ и открывает работнику (ТЗ `Cafe13KPG#553`, умолчание координатора
о разморозке).

⚠ **Код клиента в этом рецепте не читался** (правило `Cafe13KPG#975`). Всё о
встраивании — из ПАСПОРТА экрана (`Cafe13KPG#553`, комментарий паспорта,
`arhitector-ac`: `cafe13-miniapp` main `0e1a2ed`, `cafe13-api` main `d45a35f`),
слова — из ТЗ (комментарий ТЗ) и паспорта. Где объявленного нет, стоит
слово ПРЕДПОЛОЖЕНИЕ — первый адрес для описи.

| что | откуда (паспорт) |
|---|---|
| экран | `js/16-ekrany-bar.js:340` `barQueue`: живая ветка под `LIVE`, ниже демо |
| карточка заказа | `liveCard` (`js/21-navigaciya.js:177`), переходы `NEXT` (`:176`), подписи состояний `OSTATE` (`js/01-osnova.js:195`) |
| данные | `GET /bar/orders` → `QUEUE[]` = `{oid,id,state,where,pay,at,items[[title,qty]],sum\|null,who,photo,member_id}` |
| загрузка | `loadQueue` (`js/04-bar.js:191`) на входе, затем опрос раз в 8 с |
| смена состояния | `setState` → `POST /bar/orders/{id}/state` |
| вход | вкладка «Заказы» (`js/21-navigaciya.js:234`, `:280`) — сегодня на `DATA.barSide` (`admin\|bar\|curator`, `js/01-osnova.js:345`) |

## Слова шага 22

| что | слово |
|---|---|
| `Q1` действие у нового заказа | `Принять` — слово `NEXT`, своего шаг не вводит |
| `Q2` действие у готовящегося | `Готово` — слово `NEXT` |
| `Q3` действие у готового | `Выдан` — слово `NEXT` |
| `Q4` состояние заказа | подпись `OSTATE` по `state` сервера — своих слов шаг не вводит |
| `Q5` | СНЯТ поправкой к ТЗ (возврат координатора 19.11.2026): отказа очереди работнику чужого направления нет |
| `Q6` демо, ВМЕСТО прежнего обещания бота | `Новые заказы появляются на этом экране сами. Бот, если Telegram ему позволяет, ещё и пишет о них работникам направления. Принять, отметить готовым и выданным — кнопками здесь.` |

⚠ **`Q6` не обещает письма наверняка — поправка к ТЗ — третий комментарий карточки.** Telegram отказывает боту 403 МОЛЧА, если человек ему не писал, а «Старт» у бота от работника не требуется: гарантия — экран, письмо только ускоряет. Подсказки «включите бота» шаг не несёт (ТЗ).

⚠ **Ручка очереди ОДНА на две стороны** — поправка к ТЗ (замер координатора
по api `origin/main`, принят на мердже `cafe13-api#158`). Кто не барная сторона
направления, получает не отказ, а свои собственные заказы: так член клуба видит
свой заказ на `barOrder`. Поэтому работник ЧУЖОГО направления видит в его
очереди только свои заказы, если они есть, иначе пусто; 403 здесь сломал бы
покупателю экран. Код `Q5` не переиспользуется.

## Три состояния заказа в карточке

| состояние (`state`) | что в карточке | действие |
|---|---|---|
| новый (`new`) | состав `items` (название · кол-во), куда (`where`), время (`at`), `Q4` | `.btn` `Q1` |
| готовится (`making`) | то же, `Q4` | `.btn` `Q2` |
| готов (`ready`) | то же, `Q4` | `.btn` `Q3` → заказ уходит в `served` |

⚠ **Суммы работнику нет — слово владельца 18.10.2026.** Сервер не отдаёт ему
`sum` и `price` (`bar.py:932`). Карточка у работника строки суммы НЕ несёт
вовсе: ни «0 ฿», ни «—». Признак — отсутствие КЛЮЧА в ответе, а не ноль (§4).
Бар и куратор видят сумму, как видели.

## Состояния экрана

| состояние | что на экране |
|---|---|
| заказы есть | карточки по одной на заказ, три состояния выше |
| своё направление, заказов нет | прежнее пустое состояние экрана — шаг слов не вводит |
| чужое направление | только СВОИ заказы человека, если они есть, иначе пусто; не отказ (поправка к ТЗ) |
| смена состояния отклонена | `.deny` → `.verbatim`: отказ словами сервера, как есть |

**Запрещено:** показывать работнику сумму, цену, выручку и вход в `barMoney` /
`barDay` (они остаются заморожены, ТЗ); показывать работнику заказы ЧУЖОГО
направления; отменять заказ работником (отмена — возврат денег, не его зона:
умолчание сервера, принято поправкой к ТЗ);
давать работнику роль `bar` ради входа (умолчание координатора — иначе он
получил бы деньги бара); обещать кнопку в письме бота — ТЗ её не несёт.

**Проверки** — три ветви ТЗ и пять контролей (пятый — поправкой к ТЗ), по одному на защиту:

- `rabotnik-ochered` — работник видит заказы СВОЕГО направления: состав,
  куда, время, состояние;
- `rabotnik-sostoyanie` — `Принять` → `Готово` → `Выдан` двигают заказ
  new → making → ready → served;
- `rabotnik-pismo` — при покупке письмо уходит ВСЕМ работникам направления
  (случай СЕРВЕРА: клиент в этой ветви ничего не рисует);
- `rabotnik-chuzhoe-napravlenie` — работник в очереди чужого направления
  видит только СВОИ заказы и ни одного чужого. ⚠ Фикстура обязана нести заказ
  чужого направления И заказ самого человека (§5): иначе «чужих нет» не
  различает ничего;
- `rabotnik-chuzhoy-zakaz-403` — смена состояния заказа чужого направления —
  403, отказ печатается словами сервера;
- `chlen-bez-roli` — член клуба без рабочей роли: вкладки «Заказы» нет, ручка
  отказывает;
- `rabotnik-bez-summy` — в ответе очереди работнику НЕТ ключа `sum`, и в
  карточке нет строки суммы;
- `rabotnik-pismo-403` — письмо работнику, который боту не писал: в журнале
  сервера есть строка отказа с поводом и адресатом (случай СЕРВЕРА; судится
  НАЛИЧИЕМ строки, а не кодом ручки покупки).
