# `artStats` · статистика арт-директора: ивенты, мастера, деньги роли за день, неделю, месяц

**Зритель:** держатель роли `art_director`, админ проходит (право
`/stats/art`, `require_role("art_director")`; ТЗ шага 32 `Cafe13KPG#563`,
редакция 1, дробление архитектора там же). Право — видеть СВОЮ работу:
ивенты, мастеров и деньги счёта роли за период. Касса, бизнесы и членство
сюда не выносятся (ТЗ). Экрана сегодня нет, ключ `artStats` свободен.

⚠ **Код клиента не читался** (правило `Cafe13KPG#975`). Опора — ТЗ и контракт
ручки в дроблении `#563`; снимка формы сервера ещё нет (архитектор: «снимка
не ждите»). Поля, которых контракт не называет, стоят ПРЕДПОЛОЖЕНИЕМ, их
решит снимок.

**Все тексты — ключами перевода** (решение владельца №22, с шага 32): в
разметке нет ни одной русской строки этого экрана, только `slovo('<ключ>')`.
Вид ключа — `artStats.<блок>.<слот>` латиницей, подстановка — `{имя}`;
словарь — `js/00-slova.js`, экран — `js/17-ekrany-upravlenie.js` (вид
предложила рука клиента `frontend-upravlenie-a2`, рецепт его принял). Ключ,
которого нет в словаре, клиент печатает самим ключом — его видно глазом и
прогоном. Слова сервера (`detail` отказа) — не ключи: они печатаются как есть.

ролями `head` и `art_director` на «Управлении» две строки статистики — это
два предмета (ТЗ: «родственник, но другой предмет»), не повтор.

⚠ **Три надписи `N1`, `N2`, `N3` стоят ВСЕГДА, при любом числе** (ТЗ: «три
надписи, без которых экран врёт»):
- `N1` — решение владельца №30: наличные вне распределения, и страница
  говорит это прямым текстом, как касса;
- `N2` — решение №31: счёт ролевой; рядом с остатком «мои деньги» читались бы
  без неё. Мысль та же, что `R2` счёта роли (`../27/roleAccount.md`);
- `N3` — ивент берётся по `starts_at`, деньги по моменту распределения
  (`p.at`); без `N3` расхождение блоков `E` и `P` за один период выглядит
  ошибкой.

⚠ **`D1` — не `0`, а строка** (контракт дробления, AGENTS §4: «`0` с отдельным
признаком там, где 0 может значить "не посчитано"»). Имя признака назовёт
снимок формы — ПРЕДПОЛОЖЕНИЕ; без признака `0 ฿` стоит числом.

⚠ **`D2` — по уточнению контракта архитектора** (`#563`, к контракту дробления):
`balance` и `expected` — состояние «сейчас», без окна, от `C1`/`C2` не
зависят; `accrued` — за период. Без `D2` три числа одной карточки читались бы
одним периодом. Слово — продолжение `D1` шага 31.

⚠ **`E1` — ПРЕДПОЛОЖЕНИЕ по шагу 31:** там при `count = 0` `bookings` и
`collected` приходят `null`. Выборка та же (`EVENTS_SQL`); если снимок отдаст
нули, `E1` всё равно ставится по `count = 0`, а не по `null`.

растягивается по ширине, и две стрелки заняли по трети строки, а подпись
периода переломилась надвое. Стрелка — квадрат по знаку, подпись периода —
одна строка между ними.

Числа — `.num`, деньги — строкой сервера с `฿`. Внутри карточки строка —
подпись слева, число справа (`.rows > div`). Порядок мастеров — по `amount`
от большего (ВЫБОР: арт-директор ищет, кому ушло больше); равные — по имени.

## Данные экрана

- `GET /stats/art?period=day|week|month&at=YYYY-MM-DD` — одна ручка на всю
  страницу, НОВАЯ, не `/stats/club`;
- поля — по контракту дробления `#563`: `period{start,end}`,
  `events{count,bookings,collected}`, `masters[]{member_id,name,payouts,amount}`,
  `money{balance,accrued,expected}`;
- прозы в ответе нет: три надписи — ключи клиента;
- `member_id` на экран НЕ идёт: строка мастера никуда не ведёт (ВЫБОР; ТЗ
  перехода не называет);
- `balance` и `expected` — без окна, «сейчас»; `accrued` — за окно (уточнение
  контракта, `#563`);
- признак «`expected` не посчитано» — по снимку формы (ПРЕДПОЛОЖЕНИЕ).

## Перечитать на входе

Всё — на каждый вход и на каждую смену `C1`/`C2`. Числа не кэшируются между
периодами.

## Усечение

`masters[].name` — одна строка, `.clamp1`. `N1`–`N3`, `D2` переносятся, не
режутся. Числа не усекаются.
