# Café XIII — клиент мини-приложения Telegram

Статический клиент клуба Café XIII (Тонгсала, Ко Пханган): личный кабинет,
пропуск, афиша мероприятий, услуги острова, касса работника.

**Репозиторий публичный намеренно.** Эту страницу скачивает браузер каждого
гостя — секретов в ней нет и быть не может. Токен бота и данные людей живут
на стороне сервера, который проверяет подпись `initData`; он приватный.

## Состояние

С v8 приложение в Telegram работает на сервере клуба
(`https://api.cafe13.club`): кабинет, пропуск, меню и заказ бара, очередь на
баре; с v9 — открытие и закрытие смены бара и «внести себе на счёт» для
тех, кому сервер открывает кассу. Остальные разделы там помечены «ещё не
подключено». Доход и расход Бара записываются на сервер (`POST /bar/income`,
`POST /bar/expenses`): вход у куратора Бара и админа — из очереди «Заказы» и с
главной. «Отчёт за день» (v13) — `GET /bar/day`:
ручной доход и затраты строками, заказы приложения, сутки по Пхангану. С v15
афиша мероприятий берётся с сервера (`GET /events`): список с разбивкой по
дням, карточка события и вход с главной вместо «ещё не подключено». С v16 с карточки
события можно записаться (`POST /bookings`): деньги при записи не берутся —
платное оплачивается на месте, взнос добровольный; записавшимся место видно
в афише. С v17 свою запись можно
снять (`POST /bookings/{id}/cancel`): отмена спрашивает подтверждение, потому
что место возвращается в афишу и может достаться другому. Номер записи
приходит в афише; пока сервер его не отдаёт, кнопки отмены нет вовсе и на
карточке сказано об этом прямо. С v10 значок солнышка в шапке есть только у ролей god и
god_mentor из `/me`: у остальных его нет в разметке вовсе. Под ним (v12) — тестовый режим: запросы
идут с `X-Test-Mode: 1` в тестовую базу, можно выбрать человека из
`GET /act-as/people` и работать его глазами (`X-Act-As`), нажатия проходят;
над каждым экраном полоса «Тестовая база · Смотрите как …». Вне Telegram — та
же страница в режиме демонстрации: данные зашиты в `app.js` (объект `DATA`),
к серверу ни одного запроса; солнышка там тоже нет.

Живой режим **включён** с v8 (`API_ON = true` в `app.js`): клиент
ходит на `https://api.cafe13.club` с подписью `X-Telegram-Init-Data`, кабинет
берёт уровень, срок, баланс и роли из `GET /me`, согласие пишет в
`POST /me/consent`. Включён после того, как на сервере встали список
допущенных и CORS — одной выкладкой. Вне Telegram запросов нет вовсе.
Экраны, ещё не подключённые к серверу, в живом режиме честно пишут «ещё не
подключено» вместо демонстрационных чисел.

Заглушки в `tools/live.cjs` сверяются с формой настоящих ответов сервера —
`tools/api-keys.json`: только имена ключей и вложенность, без значений (в
снимках настоящий Telegram id, а репозиторий публичный). Обновить после
изменения ручек на сервере:

```bash
# подпись: ЧУЖОЙ
DUMP_DIR=<каталог вне репозитория> bash tools/check-api.sh   # в клоне cafe13-api
# подпись: ЧУЖОЙ
python3 -I tools/keys.py <тот же каталог> > tools/api-keys.json   # каталог из клона cafe13-api
```

`keys.py` отказывает, если какой-то снимок — отказ, а не ответ (статус не
200/201).

Проверка живого режима — `tools/live.cjs` (Telegram и API подменены, к
серверу не ходит):

```bash
# подпись: зелёное: 
# подпись: КРАСНОЕ
docker run --rm --memory=2g --memory-swap=2g -v $PWD:/app:ro -v <каталог-снимков>:/work -w /work \
  --entrypoint node agenthost/playwright:1.59.1 /app/tools/live.cjs
```

⚠ **`--memory` и `--memory-swap` обязательны у КАЖДОГО запуска образа, и
`--rm` тоже.** Клетка
сессии контейнер не ограничивает: `systemd-run --user --scope -p MemoryMax=2G`
доезжает до обёртки, но не до контейнера — внутри `memory.max` равен `max`
(замер мой, 31.10.2026, пара с отрицательным контролем: с `--memory=2g`
там `2147483648`; то же независимо снял `designer-55` — его числа стоят у
`indocker()` в `tools/pered-mergem.sh`). Без предела прогон, съевший
память, роняет ЧУЖИЕ прогоны на
хосте, а своя смерть от нехватки выглядит как `ENOENT` на файле в
смонтированном томе, а не как «убит».

Почему 2 ГБ: пики, снятые изнутри образа по `/sys/fs/cgroup/memory.peak` под
`--memory=2g` (31.10.2026, дерево `ae99b12`) — `shots.cjs` **629 МБ**,
`live.cjs` **500**, `vidimost.cjs` **157**. У `shots.cjs` это МАКСИМУМ из
четырёх наблюдений (629 · 238 · 235 · 233): числа разъезжаются в 2,7 раза,
причина не найдена, поэтому в предел заложен максимум, а не среднее. У двух
других — ОДНО наблюдение каждое, то есть не максимум, а просто замер; знать,
насколько они разъезжаются, пока нечем. Запас втрое к худшему известному.
Не уложится — предел правят ЗАМЕРОМ, названным числом, а не снимают.

⚠ Второй флаг не для красоты: **без `--memory-swap` docker ставит
`memory.swap.max` равным самому пределу** (замер 31.10.2026: `--memory=2g` →
`memory.swap.max=2147483648`; с `--memory-swap=2g` → `0`). То есть на хосте с
подкачкой потолок выходит ВДВОЕ выше названного — и это не запас на будущее:
подкачка тут ЕСТЬ, `SwapTotal` 8 ГБ по `/proc/meminfo` (перемерено
01.11.2026, занято 2,2 ГБ). Без второго флага потолок у этих прогонов —
настоящие 4 ГБ, а не названные 2. ⚠ Прежняя редакция абзаца говорила
«подкачки нет, флаг стоит ради других хостов»: НЕ ВОСПРОИЗВЕЛОСЬ, и вывод был
обратный правильному. Канон требует того же для процессов хоста
(`-p MemorySwapMax=0`).

Что выкладываемый `app.js` действительно живой — `node tools/api-on.cjs`
(без браузера, секунда): падает, если `var API_ON = true;` нет, если значение
другое или если объявлений больше одного.

⚠ **Подпись — приговор прибора О ПРЕДМЕТЕ, и «ПРОВЕРКА НЕ ВЫПОЛНЕНА» ею быть

работает»; объявив их подписью, проверка рецептов зеленеет ровно на той
поломке, которую должна ловить (возврат `frontend-11`, 02.11.2026: рецепт
описи без шага `cp СТАДИИ.tsv vidimost.json` проходил `rc=0`). Шаг, который
здесь проверить нечем, объявляется `# подпись: ЧУЖОЙ` — вслух, а не пропуском.

⚠ **Скрипт зовётся из `/app/tools/`, а не копией из `/work`, и это замер, а не
вкус.** Прежняя запись (`/work/shots.cjs`, `/work/vidimost.cjs`) из чистого
клона НЕ РАБОТАЛА вовсе: в `screens/` скриптов нет, а про копирование здесь не
было сказано — проверено 01.11.2026, `Error: Cannot find module
'/work/vidimost.cjs'`. Ворота звали `/app/tools/…` за всю свою историю —
`git log -S'/work/shots.cjs' -- tools/pered-mergem.sh` и то же про
`vidimost.cjs` дают ПУСТО, — то есть запуск был ОДИН рабочий и ОДИН
написанный, и расходились они молча: прибора на «рецепты из этого файла
исполняются» у нас нет. Рецепт `live.cjs` выше при этом верен с самого начала
(строка 62), так что в одном файле жили обе формы. Отсюда правило: рецепт здесь — та же строка, что у ворот. Разошлись —
прав прогон, а не файл.

`shots.cjs` — не только съёмка: он же проверяет поведение (заказ уходит с

затрата записывается тем, что ввели) и падает, если на снимаемом экране нет
его собственного признака. Признак берётся из содержимого `#view`, а не из
шапки: шапка у разных экранов одинаковая и экраны не различает.

Версия вверху `screens.html` должна совпадать с версией в демо-режиме
приложения. Разошлись — опись устарела, пересобрать.

⚠ **У пересъёмки есть ВТОРАЯ половина, и живёт она не здесь:**
`screens/cafe13-screens.pdf` собирается из `screens/print.html` отдельным

### Страница несёт ТРИ вещи: снимок, стадию и видимость

Задача владельца 27.10.2026 (`Cafe13KPG#407`): по странице должно быть видно
не только «как выглядит», но и «в какой стадии» и «кто это видит».

| что | откуда берётся | кто правит |
|---|---|---|
| снимок | `tools/shots.cjs`, живая страница 390 × 844 | автор правки экрана |
| стадия (рамка) | `screens/СТАДИИ.tsv` — ОДИН источник | автор правки; «в тесте» — координатор, «рабочий» — владелец |
| видимость | `screens/vidimost.json`: обход входов, снимает `tools/vidimost.cjs` | пересобирается вместе с описью |

Словарь стадий и весь путь экрана — `Cafe13KPG` `_docs/screen-path.md`.
Цвет рамки руками не ставится нигде: он вычисляется из стадии, иначе
страница и код разойдутся молча.

```bash
# путь шести живых людей по входам клиента — считает САМ клиент, второй реализации нет
# подпись: написан vidimost.json
docker run --rm --memory=2g --memory-swap=2g -v $PWD:/app:ro -v $PWD/screens:/work -w /work \
  --entrypoint node agenthost/playwright:1.59.1 /app/tools/vidimost.cjs
# стадия против реестра ВЫЛОЖЕННОГО клиента — падающая проверка
# подпись: зелёное
# подпись: КРАСНОЕ
python3 -I tools/check-stages.py                 # 0 сошлось · 1 красное · 2 не выполнено
# подпись: зелёное
# подпись: КРАСНОЕ
python3 -I tools/check-stages.py --самопроверка
# ⚠ ПРИ СБОРКЕ ОПИСИ — только так: подлежащее становится ЭТИМ деревом
# подпись: зелёное
# подпись: КРАСНОЕ
python3 -I tools/check-stages.py --файл app.js
```

`check-stages.py` краснеет в три стороны: «рабочий» или «в тесте» без экрана
в реестре — обещаем людям экран, которого они не видят; «нарисован» при
экране в реестре — показываем то, что считаем ненарисованным; экран в реестре
БЕЗ строки стадии — новый экран проехал мимо описи. Третий код —
`2`, «не выполнено» (файл не скачался, реестр не разобран), и читать его как
«не выполнено», а не как зелёное.

⚠ **Экран без снимка со страницы не исчезает.** Снимок делается ВНЕ Telegram,
где `LIVE` ложь, а все рабочие права начинаются с `LIVE &&` — поэтому карточки
меню, «Люди», деньги бара и касса на снимке дали бы отказ или заглушку
(замер 27.10.2026: из десяти рабочих экранов тем же прибором снимается один,
и тот в гостевом виде). Такие экраны стоят строкой без картинки: стадия,
видимость и причина. Подставлять прибору выдуманные данные нельзя — страница
обещает «то же самое открывается по ссылке», а снимок, который по ссылке не
открывается, эту фразу делает ложью. Демо-данные для них — `Cafe13KPG#409`.

⚠ **Видимость — это ПУТЬ, а не право.** Право без входа никуда не ведёт,
поэтому `vidimost.cjs` не спрашивает права списком, а ХОДИТ: от вкладок
человека по входам (`data-go`) на ОТРИСОВАННЫХ экранах, пока находятся новые.
Он же пишет, с какого экрана дверь, и страница печатает это словами.

⚠ **Вход не записывается числом в прозе.** 27.10.2026 условие видимости
карточек меню было «право `mayCards()` И вкладка „Клуб“» — по замеру, что
`data-go="barCards"` в клиенте один раз. На следующий день `miniapp#90`
поставил второй вход, на «Заказы», и это условие сказало бы о бармене ложное
«не видит» (поправка `arhitector-47`). Число вхождений устаревает чужим
мерджем; обход — нет.

⚠ **Где обход не достаёт, страница говорит это словами.** Два класса:
вход рисуется строкой данных сервера (меню, список карточек, афиша) или туда
уходит сам код, без кнопки (в карточку человека — ответом на скан пропуска).
Там условие записано как «за экраном X», и к нему приписано «обходом не
подтверждено»: «никто» у такого экрана значило бы не «пути нет», а «нечем
измерить» — разные вещи. Дверь в афишу обход всё же видит: ему подаётся
ДЕМО-НАБОР САМОГО КЛИЕНТА (`DATA.events`, та же функция строки), и такие пути
помечены «только при непустой афише». Для списка карточек и очереди
демо-набора у клиента нет, и выдумывать его прибору нельзя.

`catalog.py` держит на это три падающих проверки: экран, объявленный
выведенным из обхода, но обходом не найденный ни у кого; `за:X` с опечаткой
в адресе; `за:X`, упирающийся в экран, путь к которому не считается вовсе.
Все три проверены подлогом.

⚠ **Роли, а не имена: репозиторий публичный.** Видимость считается для шести
живых людей клуба, но в прибор, в `vidimost.json` и на страницу идут РОЛЬ и
членство — «работник бара без членства», «гость без ролей». Настоящие имена,
как и Telegram id, живут только в приватных `Cafe13KPG` и `cafe13-api`
(решение координатора 27.10.2026). Строк пять, а не шесть: двое совпадают по
роли, членству и пути дословно, и второго мерить незачем.

⚠ **Опись не должна устаревать молча — на это два падающих прибора.**

- `vidimost.cjs` пишет в `vidimost.json` **sha256 того `app.js`, с которого
  снимал**, а `catalog.py` при сборке сверяет его с лежащим рядом. Правят
  `tabList()` или вход, прибор не перегоняют — сборка краснеет: «видимость
  снята с ДРУГОГО клиента». Нет поля вовсе — «не выполнено», а не «сошлось»:
  старый файл неотличим от свежего.
- `check-stages.py` краснеет на **экране из реестра БЕЗ строки стадии**:
  новый экран иначе проезжает мимо `СТАДИИ.tsv`, а опись молчит о работающем.

⚠ **И «молчит» здесь буквально — страница не говорит «стадия не поставлена».**
Замер мой, 30.10.2026, дерево `c014829`: у экрана БЕЗ снимка строка стадии
убрана → экран исчезает со страницы ЦЕЛИКОМ (`grep -c masterApply screens.html`

### Сверка экран ↔ рецепт — шаг 7 порядка разработки

Шаг 7 (слово владельца 06.11.2026): «опись сверяет экран-рецепт». Рецепт
экрана заменил кадр, и сверять стало нечем — по снимку видно, что экран
ПОХОЖ, а взял ли сборщик названный составом ингредиент или похожий, не видно.
Поэтому `tools/shots.cjs` кладёт рядом со снимками **`razmetka.json`** — съём
отрисованных КЛАССОВ каждого снятого вида (всего и сколько из них ВИДИМЫ), —
а приговор выносит `tools/sverka-recepta.py`, сличая съём с таблицами состава
экрана и с его разделом «чего на этих экранах нет».

| вопрос | чем отвечается | чем НЕ отвечается |
|---|---|---|
| что на собранном экране есть | `razmetka.json` — отрисовка | чтением клиента: класс в коде ≠ класс на экране |
| что экрану положено | `_docs/recept/ekran/<семья>/sostav.md`: ВСЕ его таблицы, где класс в первой ячейке и КЛЮЧ экрана кодовой вставкой в последней | одной словарной таблицей: носители усечения стоят своей, отдельным разрядом |
| какие экраны у семьи | роспись `<!-- ЭКРАНЫ-СЕМЬИ: … -->` в составе | списком в приборе: копия расходится молча |
| какой экран описан этим файлом | ИМЯ файла (`<ключ>.md`) и кодовая вставка в заголовке `# ` + ключ — прибор требует их совпадения | одним из двух: оставшееся место стареет молча |
| какие шаги версии у семьи | роспись `<!-- ШАГИ-СЕМЬИ: … -->` в составе; имя каталога — ЯРЛЫК | именем каталога: витрина живёт в четырёх шагах, `15-bar` было бы ложной точностью |
| исполнен ли рецепт | «Признак сборки» рецепта, по клиенту БЕЗ комментариев, в НАЗВАННОЙ им области и до НАЗВАННОГО им числа | наличием снимка: снимок есть и у неисполненного соседа |
| область признака, когда семья живёт в ОДНОМ файле | зов соседа `tools/v-oblasti.py <файл> <ключ> '<образец>'` — тело экрана плюс функции того же файла, до которых он достаёт по вызовам | счётом `rg -c` по файлу: он считает заодно работу соседей по семье |
| радиус, цвет, усечение в стилях | `tools/check-sostav.py` дизайнера | этим прибором — вторая редакция приговора |
| ПРИЧИНА расхождения | дизайнер: «рецепт неточен» или «сборка разошлась» | прибором: он называет расхождение, а не виновного |

```bash
# подпись: самопроверка: всё как ждали
# подпись: САМОПРОВЕРКА ПРОВАЛЕНА
python3 -I tools/sverka-recepta.py --самопроверка
```

Сама сверка зовётся так — и строкой рецепта здесь НЕ стоит нарочно:

    python3 -I tools/sverka-recepta.py     # 0 сошлось · 1 расхождение · 2 не выполнено

⚠ **Почему прозой, а не рецептом.** Её законный ответ на сегодня — `2`: шага
13 в клиенте нет, и «рецепт ещё не исполнен» — это ответ О ПРЕДМЕТЕ, а не «мне
не дали входа». `tools/check-recepty.py` читает код 2 у любого рецепта как
поломку рецепта (и правильно читает — у соседей по воротам двойка значит
ровно это), поэтому рецептом стоит самопроверка, у которой приговор от дерева
не зависит. Когда шаг соберут и сверка станет зелёной, вызов обязан встать
рецептом — иначе он состарится молча, как уже старели `/work/shots.cjs` и
рецепт описи без `cp СТАДИИ.tsv`.

⚠ **`razmetka.json` — часть описи, а не побочный файл прогона:** при
пересъёмке он переносится в `screens/` вместе со снимками, тем же PR. Не
перенесли — сверка скажет «съём снят с другого дерева», и это верно.

⚠ **Съём стареет, и на это падающая проверка.** `razmetka.json` несёт слепки
страницы, с которой снят (та же карта, что у видимости), и сверка сравнивает
их свод со сводом дерева: разошлись — «не выполнено», а не приговор по
прежним классам. Правка клиента без пересъёмки описи обязана это зажигать.

⚠ **Три исхода, и двойка не зелёное.** `0` — все ингредиенты состава найдены
на своих экранах, запрещённых классов на них нет. `1` — расхождение:
ингредиента нет ни на своём экране, ни на одном снятом виде; ингредиент лежит
в разметке ПОГАШЕННЫМ (на экране его нет, а по разметке он выглядел бы
положенным); запрещённый составом класс на экране есть. `2` — сверять нечем:
рецепт ещё не исполнен, признак сборки сошёлся частично, рецепт исполнен, а в
съёмке описи экрана нет, съём снят с другого дерева, форма состава или рецепта
сменилась.

⚠ **ПРИЗНАК СБОРКИ НЕСЁТ ОБЛАСТЬ И ЧИСЛО, и прибор соблюдает оба.**
Путь в строке `rg` — часть признака: замер 06.11.2026 — `rg -c 'Попробовать
снова' js/16-ekrany-bar.js` даёт **1**, а тот же шаблон по всему клиенту —
**15 в восьми файлах**. Поиск по складке всего клиента спрашивал бы ШИРЕ, чем
назвал рецепт. А слова «обязано стать N» объявляют признак ТРЕБОВАНИЕМ: у
ОТТАИВАЕМОГО экрана ключ в клиенте уже есть, и рецепт требует другого СЧЁТА —
у `bar` «Попробовать снова» 1 → 0, у `drink` «Меню не загрузилось» 1 → 2
(состояние разводится на два экрана). Двоичного «есть/нет» на это не хватает:
второй случай им не выражается вовсе, а находкой он истинен уже сегодня.
Прочитав требование как находку, прибор переворачивает приговор МОЛЧА —
«исполнен» ровно до сборки и «не исполнен» после неё. Цель вяжется к ближайшему
предшествующему ЗАМЕРУ — любой из двух форм (в одном абзаце признаки бывают
разнородны) — и печатается в выводе числом.

⚠ **ОБЛАСТЬ ПРИЗНАКА — ЭКРАН, А НЕ ФАЙЛ, и это вторая форма замера.** Когда
семья живёт в одном файле (витрина бара — пять экранов в `js/16-ekrany-bar.js`),
счёт `rg -c` по файлу считает заодно работу соседей. Замер `designer-55` по
сданной витрине: из пяти признаков формы `rg` верны были ДВА, а два — **ложно
зелёные**: `drink` ждал «Меню не загрузилось» = 2 и получил 2, но ни одной в
своей области (одна в помощнике `menuGate`, другая у соседа `bar`); `barOrder`
ждал «Заказ не загрузился» = 1 и получил 1 — находка в помощнике `mineFail`.
Не позови сборщик помощника из экрана, оба признака сказали бы ТЕ ЖЕ ЧИСЛА,
то есть не отличали исполненного от неначатого. Поэтому признак записывается
зовом:

    python3 -I tools/v-oblasti.py js/16-ekrany-bar.js drink 'Меню не загрузилось'

Область считает СОСЕДНИЙ прибор (дизайнер), а сверка его ЗОВЁТ: своей
реализации обхода у неё нет нарочно — прибор, проверяющий чужую работу второй
реализацией того же, сверяет себя. Ключ в зове обязан совпасть с ключом
рецепта (ПАДАЮЩАЯ проверка, третье место той же пары): признак, целящий в
область ЧУЖОГО экрана, — тот же дефект, только объявленный. РАЗВИЛКА берёт ту
же команду, исходы — после закрывающей кавычки образца.

⚠ **Три отказа зова, и ни один не зелёный:** прибора в дереве нет, прибор упал,
прибор напечатал не число — замера НЕТ, и это `2`, «нечем спросить». Читать
двойку как проходную — ровно та ошибка, против которой стоит различение
«не выполнено» ≠ «сошлось».

⚠ **ПРЕДЕЛ ОБЛАСТИ НАЗВАН: обход идёт только по НАЗВАННОМУ ФАЙЛУ.** Помощник,
уехавший в другой файл (`tile`, `buyBtn`, `stepper`, `barRow` — в
`js/21-navigaciya.js`), в область не входит, и признак на его слово краснеет
ЛОЖНО. Замер 06.11.2026: `drinkbtn`, `btn mini`, «Бар закрыт», «Не хватает» в
`js/16-ekrany-bar.js` встречаются **0** раз и живут в `js/21-navigaciya.js`.
Край выбран в сторону строгости — красное с адресом дешевле зелёного без
него, — и сверка повторяет этот предел в своём отказе, чтобы его не прочли
как её дефект. Признак, чей предмет ШИРЕ одного файла, пишется формой `rg`
(путь или каталог), а список файлов через запятую зов не принимает: сосед
говорит «файла нет», и сверка называет это своим текстом.

⚠ **Проза признак не покупает, и в новой форме тоже.** Сосед комментарии НЕ
снимает (замер: вставка фразы комментарием в тело `drink` живого
`js/16-ekrany-bar.js` поднимает его счёт с 0 до 1), поэтому сверка зовёт его
ДВАЖДЫ — по копии без комментариев и по файлу как он есть, — выносит приговор
по КОДУ и НАЗЫВАЕТ расхождение числами. Иначе `// TODO: Меню не загрузилось`
делало бы требование «обязано стать 1» зелёным.

⚠ **Словарная строка — та, где КЛАСС в первой ячейке.** В составе есть таблицы
другого устройства («помощник · адрес · что кладёт», «где · живой · демо»), и
читая их последнюю ячейку как «где», прибор принимал за ключ что попало. Имена
помощников при этом собираются и становятся известными не-ключами: в ячейке
«где» они стоят законной прозой («`bar` — плитка позиции (`tile`)») и от ключа
синтаксически неотличимы. Без обоих правил прибор краснел бы на верной работе,
а ложное красное учит не верить прибору, а не чинить предмет.

⚠ **Чего прибор не судит — названо числом в его же выводе.** Классы состава
без вставки ключа в ячейке «где» (у шага 13 их 10 из 24 — слова «все подписи»
прибору не ключ) не привязаны ни к одному экрану и не судятся. Классы,
названные НЕ первой ячейкой строки, — тоже: так в составе витрины стоят 10
ингредиентов из таблицы ПОМОЩНИКОВ (`.plain`, `.drinkbtn`, `.tile`,
`.stepper`, четыре вида кнопки покупки), и их отрисовку не спрашивает никто,
пока класс не получит своей строки словаря с ключом. ДЕМО-ВЕТКА не судится
отдельной строкой: съём идёт вне Telegram, где `LIVE` ложь, и класс,
помеченный составом `ТОЛЬКО демо`, в снятой ветке стоит законно. ШАГ ВЕРСИИ
БЕЗ СЕМЬИ спрашивается только с `--шаги <файл>`: списка шагов версии в этом
репозитории НЕТ (канон — `Cafe13KPG` `_docs/owner-sources/shagi-razrabotki.md`),
а копия его старела бы молча; столкновение двух семей на одном шаге прибор
краснит и без списка. Состояния рецепта (отказ, пусто, отправка, вспышка) опись не снимает
— класс, живущий только в них, печатается как НЕ ИЗМЕРЕНО, и закрывает это
съёмка состояния фикстурой, а не послабление приговора. Класс ОБОЛОЧКИ
(`.bar`, вкладки — они в `index.html`) есть на каждом снятом виде, и прибор
это МЕРИТ, а не угадывает списком: такая строка печатается как признак шире
предмета.

## Палитра — снята с места, не придумана

Фирменного цвета у заведения нет: в логотипе 244 оттенка и все ахроматические,
знак — тёплый угольный `#2B2A28` на белом. Дневные цвета взяты из интерьера
(горчичный бархат, сансевиерия, лососевая банкетка), ночные — из вечернего
света (магента, янтарь). Переключение день/ночь — свойство самого места,
поэтому тема следует за темой Telegram, а пропуск всегда ночной: его
показывают у двери вечером.

Заголовки набраны брусковым шрифтом, потому что в знаке римские цифры `XIII`
брусковые.

## Чего здесь нет

- приёма платежей: счёт пополняют у хостес, приложение лишь тратит его —
  на баре в первой версии платят только со счёта, при заказе;
- проверки подписи `initData`: это работа сервера, в браузере она
  бессмысленна;
- настоящего кода пропуска в демонстрации: там узор, и так и подписано. В
  живом режиме код выдаёт сервер (`GET /pass`), QR рисуется из него
  библиотекой `vendor/qrcode-1.4.4.js` (qrcode-generator, MIT, sha256
  `18ae399f…1bf1780`, сверено по jsdelivr и unpkg) и сохраняется на телефоне,
  чтобы у двери без сети пропуск всё равно открылся;
- фотографий напитков: на их месте цветные плитки и пометка «без фото».
  Картинку из каталога ставить нельзя — гость закажет не то, что увидел.
  Фотография появляется, когда снимок пройдёт путь с экрана «Съёмка».
